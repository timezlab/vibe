# Harness Foundation (Phase 1)

**Status:** planned
**Owner:** Liam Lee
**Last updated:** 2026-07-22

## Problem

Teams using Claude Code accumulate rules, skills, agents, and hooks per
developer and per repository. There is no canonical, installable set — every
copy drifts, and nothing learned in one project transfers to the next.

## Goals

- A minimal canonical harness set in this repository: `rules/`, `agents/`
  (3–4 agents), `commands/`, `hooks/` (memory hooks), with common and
  TypeScript rule packs.
- A canonical content format plus a `vibe sync` specification that compiles it
  to the Claude Code target first (`CLAUDE.md` / `.claude/`).
- A simple installer so a repository can adopt the harness in one step.

## Non-goals

- The local web UI (Phase 2+).
- Cross-harness parity beyond the cheap `AGENTS.md` target — Cursor and
  deeper adapters come when the team needs them.

## Solution sketch

Canonical content lives here once. An adapter per platform declares its write
targets, transform, and capability matrix; `vibe sync` compiles canonical
content into generated outputs carrying a "generated by vibe" header
([ADR 0004](../decisions/0004-compile-canonical-content-through-adapters.md)).
The directory layout stays Claude-plugin-compatible so the distribution
decision remains open
([ADR 0005](../decisions/0005-use-a-claude-compatible-plugin-layout.md)).

## Success conditions

- A fresh repository can install the harness and get working Claude Code
  rules, agents, commands, and hooks without hand-copying files.
- Regenerating outputs after editing canonical content produces no manual
  merge work.
- No platform output in any consuming repo is hand-edited (verified by the
  generated-file header).

## Open questions

- Distribution mechanism (plugin / npx skills / installer / hybrid) — decide
  after Phase 1 evidence; tracked as a [roadmap gate](roadmap.md#open-decision-gates).
- Exact canonical file format for rules/agents — decided in the Phase 1
  feature spec when work starts.
