# VIBE Documentation Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the stale skills-repository documentation with an English, lifecycle-first VIBE documentation system and initialize the latest stable Spec Kit without consuming feature number `001`.

**Architecture:** Root files are short entry points for humans and agents; durable product intent and accepted rationale live under `docs/`; qualifying execution work will later live under `specs/`. Spec Kit owns `.specify/` and its Claude integration, while VIBE's constitution records only standing project invariants.

**Tech Stack:** Markdown, GitHub Spec Kit `specify-cli==0.13.0`, Claude Code integration, Agent Skills validator `skills-ref==0.1.1`, Git.

## Global Constraints

- English is the canonical documentation language.
- VIBE remains explicitly pre-alpha; do not present `vibe`, `vibe ui`, or `vibe sync` as implemented commands.
- Do not create `specs/`, a numbered feature folder, or any artifact consuming `001`.
- Do not create empty `docs/guides/`, `docs/reference/`, or `docs/concepts/` directories.
- Preserve unrelated and pre-existing untracked files; stage only paths named by the active task.
- `AGENTS.md` must stay at or below 150 lines, and `CLAUDE.md` must contain exactly `@AGENTS.md` plus its final newline.
- Link to canonical facts instead of copying them between files.
- Use the installed stable CLI's help when it differs from the skill snapshot.

- [ ] **Step 6: Seed the VIBE constitution**

Replace template placeholders in `.specify/memory/constitution.md` with six enforceable principles:

1. **Canonical Sources, Generated Targets** — canonical harness content is edited once; adapter outputs carry a generated-file warning and are never hand-maintained.
2. **Explicit Capability Degradation** — every adapter declares supported and unsupported capabilities; unsupported behavior degrades visibly rather than silently.
3. **Human-Approved Learning** — session-derived instincts remain pending until a person approves them; only approved instincts load into future sessions.
4. **Safe Repository Mutation** — merge-sensitive config changes are add-only and preview-first; worktree and filesystem operations resolve explicit targets before mutation.
5. **Documentation Ships with Code** — public surfaces, boundaries, decisions, and debt update in the same change as implementation.
6. **Observable Verification** — completion claims name and run the command or observable check that proves the outcome.

Add governance stating that accepted ADRs are append-only, Spec Kit is used only above the size gate, completed specs graduate durable knowledge, and constitution amendments include a dated rationale.

- [ ] **Step 1: Write the standing product direction**

Create `docs/product/DESIGN.md` with these sections and facts:

- `Status`: pre-alpha; `Last updated`: 2026-07-22.
- **Problem:** agent tooling is fragmented across harness configuration, parallel workspaces, and learned project context.
- **Product:** VIBE means Vibe Integrated Build Environment and combines harness content, a local multi-agent workspace, and human-governed learning.
- **Users:** developers and teams using Claude Code first, then other CLI harnesses through adapters.
- **Goals:** one canonical harness source, `vibe ui` as the eventual local workspace, safe parallel sessions, and reusable approved learning.
- **Non-goals:** fully autonomous learning, deep support for every harness in Phase 1, a desktop application, and remote hosted infrastructure.
- **Experience:** Harness Setup, multi-pane Workspace, and Learning surfaces, all labeled planned.
- **Success:** Phase 1 can install/sync canonical content for Claude without maintaining copied outputs.

- [ ] **Step 2: Write the roadmap and Phase 1 product spec**

Create `docs/product/roadmap.md` with four phases from the approved decisions, mark Phase 1 as current, label later phases planned, and include two explicit decision gates: Phase 2 HTTP framework and harness distribution mechanism. Keep the repository/GitHub/npm administrative checklist here.

Create `docs/product/harness-foundation.md` with `Status: planned`, the target users and problem, goals for canonical content plus Claude-first sync, non-goals for UI and deep cross-harness parity, a solution sketch, observable success conditions, and the two distribution questions that remain open.

- [ ] **Step 3: Write ADRs 0001 and 0002**

Use the ADR template with `Status: accepted`, `Date: 2026-07-22`, and `Deciders: Liam Lee`.

For ADR 0001, decide on a local web application with Node.js and TypeScript end-to-end, `node-pty` on the server, `xterm.js` in the browser, and Dockview as the leading layout candidate. Reject Rust, Python, a desktop-first shell, and a tmux-only wrapper for the reasons already recorded. State the cost of Node native PTY packaging and the invariant that browser UI never owns PTY processes.

For ADR 0002, decide on worktrees under `<project>/.vibe/worktrees/<branch>/`. Reject multiple branches in one working tree and external untracked workspace locations. State the `.vibe/` ignore/exclude obligations and the invariant that cleanup resolves a specific registered worktree before removal.

- [ ] **Step 4: Write ADRs 0003 through 0005**

For ADR 0003, decide on file-based, per-project instincts with pending and approved states. Reject fully automatic learning and session summaries without reusable instincts. State that only approved instincts load.

For ADR 0004, decide on one canonical harness representation compiled by capability-declaring adapters. Reject hand-maintained per-platform copies and a Claude-only permanent format. State that generated targets have a warning header and merge-sensitive global config uses add-only dry runs.

For ADR 0005, decide to organize current harness content as a Claude-compatible plugin while leaving final distribution open. Reject choosing a single installer before Phase 1 evidence and maintaining layouts for every possible channel. State that this ADR must be revisited when the distribution gate is resolved.

Every ADR must include at least one specific rejected alternative, non-empty Better/Worse/Must-now-be-true subsections, and a concrete revisit signal.

- [ ] **Step 5: Create the debt log and navigation index**

Create `docs/tech-debt.md` with a statement that no debt is recorded yet and an HTML comment containing the required entry fields: ID, Where, Symptom, Why deferred, Trigger to fix, and Created. Do not convert undecided product choices into debt.

Create `docs/index.md` as navigation only. Link the root architecture/entry docs, three product documents, five ADRs, tech debt, the approved design record, and this implementation plan. Give each link exactly one descriptive line.

- [ ] **Step 6: Replace the monolithic decision log with a migration pointer**
